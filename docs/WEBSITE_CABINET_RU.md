# Личный кабинет MinETRO

`/account.html` открывает кабинет после входа в существующий аккаунт Supabase.

- Ник и почта — только для просмотра; редактора ника и PATCH ника на сайте нет.
- Скин: PNG до 256 КБ, Steve 64×32/64×64, Alex 64×64. Проверяются заголовок,
  размеры и декодирование; браузер перепаковывает PNG без исходных метаданных,
  сохраняя высоту 32 для старого формата. Предпросмотр — развёртка текстуры.
- Скин сохраняется в существующий приватный `skins/<user UUID>/skin.png`,
  а путь/модель — в собственный профиль. Сайт и лаунчер используют один профиль.
  Показ в игре пока не подключён.
- Восстановление/смена пароля — письмо Supabase, без передачи пароля разработчику.
  Ограничения встроенной почтовой отправки остаются; отдельный SMTP не настроен.
- Заявка dev уникальна для аккаунта и создаётся только подтверждённым пользователем.
  Повторная отправка не создаёт дубль и не сбрасывает решение.
- Администратор видит входящие с ником, временем, статусом и кнопками
  **Подтвердить / Отклонить**. Входящие обновляются вручную и раз в минуту,
  пока кабинет открыт. Решение, время и UUID администратора сохраняются сервером.
- RLS и RPC не позволяют пользователю выдать себе роль или подтвердить заявку.
  Администратор может рассматривать и собственную заявку; конкурирующее решение не перезаписывает принятое.

## Подготовка сервера

Применены миграции `202610300002_dev_access.sql` и `202610300003_admin_self_review.sql`
из `launcher/supabase/migrations/`. По прямому указанию владельца роль администратора
назначена существующему подтверждённому аккаунту **Cotuna**. Привязка выполнена
по UUID аккаунта в `launcher_admins`; ник сам по себе не предоставляет роль. Секретных ключей в
браузере нет.

Миграция управляет только заявками. Она не публикует архив, не раскрывает ссылку
Google Drive и не подключает сборку к лаунчеру. MinETRO недоступно; dev-скачивание
тоже пока закрыто, даже после одобрения заявки: требуется безопасная доставка и
проверка архива. Будущие обновления — только после явного разрешения владельца.

## Проверки

- `node --test tests/website_accounts.test.mjs`: протокол аккаунта/скина/dev,
  восстановление пароля, гостевой/пользовательский/административный интерфейс.
- `python -m unittest discover -s tests -p 'test_beta_website.py'`.
- `python -m unittest discover -s tests -p 'test_website_wiki*.py'`.
- `tools/test_website_cabinet_browser.mjs`: Chromium, 320/390/768/1024/1440 px,
  проверка переполнения, вход/выход, dev-заявка, загрузка и повторное чтение PNG,
  сохранение старого 64×32 формата, письмо восстановления, оба решения администратора.
  Все Auth/Storage запросы браузерного теста подменены; реальные аккаунты не меняются.
  Нужен `playwright-core` и браузер; пути можно указать через `PLAYWRIGHT_MODULE` и
  `CHROMIUM_EXECUTABLE_PATH`. Для serverless Chromium предусмотрен `CHROMIUM_MODULE`.
- `launcher/supabase/tests/dev_access.sql`: отрицательные проверки прав на реальном
  backend, без создания пользователей и назначения администраторов; транзакция откатывается.

Доставка письма на настоящую почту, сохранённое одобрение реальным администратором
и Minecraft не проверялись. Подтверждение собственной ожидающей заявки Cotuna
проверено на backend внутри откатываемой транзакции: сама заявка оставлена
ожидающей, чтобы владелец мог подтвердить её самостоятельно. Пароли и сеансы хранятся только в памяти страницы;
после обновления страницы требуется повторный вход.

## Правило публикации

Автоматическая сборка лаунчера больше не публикует ZIP в ветку при обычном push.
Для отдельной тестовой публикации нужен ручной workflow_dispatch с явно включённым
`publish_test_launcher` и предварительное разрешение владельца. Изменения backend
в `launcher/supabase/` сами по себе больше не запускают сборку Windows-лаунчера.
Проверки сайта в `.github/workflows/website.yml` не публикуют сборки или обновления.
