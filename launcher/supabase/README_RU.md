## Уже настроено

* Применена миграция `minetro_profiles_and_private_skins`; исходный SQL находится
  в `migrations/202610300001_accounts.sql` (повторно на этот проект не выполнять).
* Включены Email/Password signup, подтверждение почты и ротация refresh-токенов.
  Phone и anonymous signup выключены. Автоподтверждение email не включалось.
* Приватный bucket `skins`, лимит 256 КБ, MIME image/png. Таблица профилей имеет RLS.
* В конфигурации лаунчера опубликован только publishable key, не `service_role`.
* Развёрнута функция `account-confirmed`, она установлена как `site_url` Auth.
  Это только текстовая посадочная страница после ссылки подтверждения: токены
  не читает/не хранит, регистрацию сама не подтверждает и доступ не выдаёт.
* Живой rollback SQL-тест двух пользователей прошёл: собственные профили/объекты,
  запрет чужих изменений, запрет изменения id, case-insensitive ник и анонимные
  отказы. Фикстуры откатились, дополнительный аудит подтвердил 0 users/profiles.
* Из Windows CI прошли живые HTTP-проверки публичного Auth settings, анонимных
  отказов REST и текстовой посадочной страницы. Это не полноценный вход пользователя.

## Перед публичным запуском — ещё нужно

1. Настроить собственный SMTP в Dashboard → Authentication → Email / SMTP.
   Встроенная почта Supabase ограничена, доставка всем пользователям не проверена.
   Не присылать пароли SMTP/БД, `service_role` и `sb_secret_…` в чат или Git.
2. Выставить серверный минимум пароля **12**, сейчас Supabase имеет стандартные 6.
   Клиент уже требует 12–128 символов, но клиентская проверка не заменяет серверную.
3. Для цифровых кодов добавить `{{ .Token }}` в Confirm signup и Reset password
   templates, проверить доставку/истечение/повтор и только затем переключить
   публичную конфигурацию `emailCodesEnabled` в true и выпустить новую сборку.
   Сейчас false: подтверждение по штатной ссылке с возвратом в лаунчер для входа;
   recovery-коды скрыты, чтобы не предлагать заведомо ненастроенный процесс.
4. Проверить живой сценарий: signup → письмо → подтверждение → вход → смена ника →
   PNG upload/download → выход; двумя разными пользователями проверить HTTP RLS.
   Реальные письма, пользовательский вход и HTTP skin upload пока не проверялись.
5. Проверить ограничения частоты/anti-abuse для публичного запуска. CAPTCHA UI и MFA
   в desktop-клиенте ещё нет; не включать обязательную CAPTCHA без её интеграции.

Доступный коннектор предоставляет только часть Auth config и не позволяет менять
SMTP/шаблоны/password_min_length через свой input_schema. Их надо настроить в
Dashboard; почтовая верификация не отключалась ради обхода этого ограничения.

## Данные и безопасность

`profiles` создаёт ограниченный auth trigger. Пользователь читает/меняет только свою
строку; нельзя INSERT/DELETE и менять id/created_at. Ник: 3–16 ASCII букв/цифр/_,
уникальность без учёта регистра. Почта остаётся в Auth, не в публичном профиле.

Storage RLS разрешает ровно `USER_UUID/skin.png`, не произвольные папки. Bucket
не публичный. Клиент декодирует PNG 64×64 / 64×32 и перекодирует его, однако bucket
проверяет только размер/MIME, **не изображение**: для будущей раздачи скинов в игре
нужна серверная валидация PNG и отдельный безопасный skin API, а не открытие bucket.

Один фиксированный skin object предотвращает накопление версий. Upload и смена
skin_model — два запроса, не общая транзакция; при частичной ошибке обновить профиль
или повторить. Автоматического удаления storage при удалении auth user пока нет.

Сеанс только в памяти, пароли и токены не пишутся на диск. После выхода основной
лаунчер блокируется; перед установкой, игровым запуском и открытием папки проверяется
сеанс/свой профиль. Это барьер штатного клиента, не DRM публичных GitHub assets.
Аккаунт MinETRO не подменяет Microsoft и не даёт лицензии Minecraft.

Маскированные HTTP ошибки не выводят сырые ответы/SQL/токены. Скины и данные
аккаунта MinETRO не передаются в Prism. Live game/skin integration пока отсутствует.
