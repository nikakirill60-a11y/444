# Аккаунты MinETRO / Supabase — подготовка подключения

Состояние: клиентский код и SQL подготовлены, **живой Supabase пока не подключён**.
`launcher/accounts.public.json` намеренно содержит пустые значения. Никаких паролей,
ключей администратора или фиктивных регистраций в репозитории нет.

## Что реализовано

* Регистрация email + пароль + уникальный ник (3–16 латинских букв, цифр, `_`).
* Подтверждение почты цифровым кодом, вход, выход, восстановление пароля кодом.
* Свой профиль, смена ника; уникальность без учёта регистра обеспечивается БД.
* Выбор локального PNG, проверка размеров 64×64 / 64×32 и лимита 256 КБ,
  декодирование и повторное PNG-кодирование без исходных метаданных.
* Двумерный pixel-art предпросмотр спереди/сзади, Steve / Alex (Alex только 64×64).
* Загрузка скина в приватный bucket, чтение своего скина после входа.
* Сеанс только в памяти; обновление истекающего токена, выход с очисткой локального
  сеанса даже при сетевой ошибке. Пароли и токены не записываются на диск.

Это **отдельная учётная запись MinETRO**, не Microsoft/Minecraft session server.
Скин пока виден в профиле, а **не в игре другим игрокам**. Для игры ещё нужны полный
модпак и согласованная интеграция клиента/сервера. Приватный bucket не открывать
целиком ради показа в игре; для этого нужен отдельный проверенный публичный skin API.

## Подключение, когда будет доступ

1. Подключить Supabase через предусмотренное Arena подключение, когда оно будет
   готово. Не присылать пароли БД и `service_role` / `sb_secret_…` в чат.
2. На тестовом проекте применить `migrations/202610300001_accounts.sql` один раз
   от администратора. Сначала проверить, что таблицы `profiles` и bucket `skins`
   не заняты чужим приложением. Миграция намеренно не удаляет существующие данные
   и не маскирует конфликты `IF NOT EXISTS`.
3. В Supabase Auth включить Email/Password и **Confirm email**, минимальную длину
   пароля 12, ограничения частоты запросов, email OTP expiration и надёжный SMTP.
   Сессии/пароли обслуживает Supabase Auth, собственная таблица паролей не нужна.
4. В шаблонах **Confirm signup** и **Reset password** добавить цифровой код
   `{{ .Token }}`. Клиент использует `/auth/v1/verify` с типом `signup` или `recovery`.
   Он не перехватывает URL-токены, не просит копировать access/refresh token из
   адресной строки. Пока шаблоны не настроены, восстановление с кодом не считать готовым.
   Если включена обязательная CAPTCHA, нужен отдельный UI CAPTCHA — текущий
   desktop-клиент его ещё не поддерживает; не отключать защиту рабочего проекта
   вслепую. Сначала выбрать/проверить подходящую anti-abuse стратегию для desktop.
5. В `accounts.public.json` указать **только** URL проекта вида
   `https://PROJECT.supabase.co` и его **publishable** (либо legacy `anon`) ключ:

   ```json
   { "url": "https://PROJECT.supabase.co", "publicKey": "sb_publishable_…" }
   ```

   Это публичная конфигурация desktop-клиента, не секрет. Привилегированный ключ
   здесь недопустим, его тип дополнительно блокируется клиентом. Ключ `anon` не
   заменяет RLS. Сетевые перенаправления в клиенте аккаунтов отключены, чтобы не
   отправлять пароли/JWT на другой адрес. Кастомные домены пока не поддерживаются.
6. Выполнить `tests/ownership.sql` в изолированном Supabase проекте. Фикстуры двух
   пользователей откатываются транзакцией. Дополнительно провести живые HTTP-тесты
   двух пользователей: чужой профиль/скин не читается и не перезаписывается,
   неподтверждённый email не входит, пароли восстанавливаются, rate limits действуют.
7. Собрать и проверить Windows-клиент, затем публиковать подключённый канал аккаунтов.
   Сам лаунчер не предлагает вводить ключи и не доверяет удалённой смене backend.

## Правила доступа и ограничения

* `public.profiles`: SELECT и UPDATE только своей строки; изменение `id`/`created_at`,
  INSERT/DELETE клиентом запрещены. Профиль создаёт ограниченный auth trigger.
* `skin_path` может быть только `USER_UUID/skin.png` либо null. Storage RLS ограничен
  ровно тем же объектом. Анонимного доступа нет. При удалении auth-пользователя
  профиль удаляется FK; storage-объект администратор удаляет отдельно (автоматической
  функции удаления аккаунта в UI пока нет).
* Bucket ограничивает MIME/размер, но **не декодирует PNG**: проверки размеров и
  перекодирование сейчас клиентские и обходятся сторонним HTTP-клиентом. Для
  публичной раздачи скинов в игре понадобится серверная валидация изображений.
* Хранится один объект на пользователя, поэтому нет накопления версий. Замена
  storage-объекта и обновление `skin_model` в БД — два запроса, не общая транзакция.
  При ошибке второго запросить профиль заново/повторить загрузку: часть изменений
  могла уже сохраниться. Нельзя сообщать пользователю об успехе до обоих ответов.
* Профили и скины не публичны, почта остаётся в Supabase Auth. Поддержка MFA,
  запоминания входа, смены email и полного удаления аккаунта не реализована.
* Результаты API не выводятся как сырые SQL/JSON ошибки; секреты не логируются.
  Содержимое скина/локальные пути также не отправляются в Prism.
* SQL ownership-тест подготовлен, но **ещё не выполнен на Supabase**; mock HTTP и
  Windows smoke не доказывают правильность настройки живого проекта.
